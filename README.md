# IG External Profiles

Render profiles from dependency packages (for example `ISiKPatient` from ISiK) in a FHIR Implementation Guide, with
differential, snapshot, must-support view and definitions, **without adding them to the IG's package**.

Typical case: your IG uses a profile from another IG unchanged and does not want a derived profile of its own just
to get a profile page.

## How it works

The IG Publisher renders profile tables only for resources of the IG itself. The script therefore builds a
**helper IG** that contains the requested profiles as its own resources:

1. Create the helper IG with the same dependencies and the same language as the target IG
2. Copy the profiles from the package cache (`~/.fhir/packages`); SUSHI downloads missing packages
3. Run SUSHI and the IG Publisher. The publisher is stopped as soon as the fragments are written (before Jekyll),
   which saves several minutes
4. Take the fragments from `temp/pages/_includes`, rewrite links into the definitions page to anchors on the same
   page, and write them to `input/includes/` of the target IG

The target IG's package only receives HTML, no StructureDefinition.

## Configuration

`external-profiles.yaml` in the IG directory:

```yaml
profiles:
  - id: ISiKPatient                 # id of the StructureDefinition in the package
    package: de.gematik.isik#5.1.1  # package#version, must match sushi-config.yaml if listed there
    page: extern-ISiKPatient.html   # optional: page the profile is shown on (for cross links)
    link: https://...               # optional: link to the original page (default: Simplifier resolver)
    disclaimer: false               # optional: no notice box; a string replaces the default text
output: input/includes              # optional
data: input/data                    # optional: folder for external_profiles.json
template: fhir.base.template#current  # optional: template of the helper IG
lang: de                            # optional: label language (default: i18n-default-lang of the IG, else en)
fragments: [diff, snapshot, snapshot-by-mustsupport, dict]  # optional
```

For each profile the script writes:

| File | Content |
|---|---|
| `extern-<id>.html` | Page include: notice box, description, info table, tabs (differential, snapshot, must support), definitions |
| `extern-<id>-disclaimer.xhtml` | Notice box: external profile, not part of this IG's package, the publisher's specification is authoritative |
| `extern-<id>-{diff,snapshot,snapshot-by-mustsupport,dict}.xhtml` | Fragments as generated by the IG Publisher |
| `extern-<id>-info.xhtml` | Canonical, version, status, package, publisher, base, link to the original |
| `extern-<id>-description.xhtml` | Description of the profile (Markdown) |

In addition it writes `input/data/external_profiles.json` with id, title, canonical, version, package, publisher, page
and the resolver links the publisher would otherwise generate for each profile. With the IG parameter
`path-data: input/data` the publisher passes it to Jekyll as `site.data.external_profiles`, so a template can, for
example, point the artifacts page to the profile pages (see below).

The files are generated, add them to `.gitignore`:

```gitignore
/input/includes/extern-*
/input/data/external_profiles.json
```

The notice box uses the classes `stu-note external-profile-note`: it looks like the base template's STU note unless a
template styles `external-profile-note`.

## Usage

### On a page

```liquid
{% include extern-ISiKPatient.html %}
```

Use one page per profile, because the tabs and anchors use fixed ids.

### GitHub Actions

Inside a job that runs in an IG Publisher container, after the dependencies are loaded and before the build:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    container:
      image: ghcr.io/gefyra/ig-publisher-with-snapshot-support:latest
    steps:
      - uses: actions/checkout@v5
      # ... load dependencies, SUSHI ...
      - uses: Gefyra/ig-external-profiles-action@v1
      # ... IG Publisher ...
```

| Input | Default | Meaning |
|---|---|---|
| `ig-dir` | `.` | Directory of the IG |
| `config` | `external-profiles.yaml` | Configuration file, relative to `ig-dir` |
| `publisher-jar` | – | Path to `publisher.jar`; otherwise `input-cache/publisher.jar`, then `/opt/ig/publisher.jar` |

### Locally

Requirements: `java`, `node`, `sushi` and a `publisher.jar` (for example `input-cache/publisher.jar` after
`_updatePublisher`).

```bash
node path/to/bin/ig-external-profiles.js --ig .   # in the IG directory
./_genonce.sh
```

`--keep` keeps the helper IG for debugging; its path is printed.

### On the artifacts page (template)

The publisher links global profiles from packages without a web URL to `simplifier.net/resolve`. A template can
override the base template's `artifacts.xml`, capture its output and replace each entry of `resolverUrls` with `page`:

```liquid
{% capture artifacts %}{% include fragment-artifacts-table.html %}{% endcapture %}
{% for p in site.data.external_profiles.profiles %}{% for r in p.resolverUrls %}{% assign artifacts = artifacts | replace: r, p.page %}{% endfor %}{% endfor %}
{{ artifacts }}
```

Without the data file the loop does nothing, so the override is safe for IGs that do not use this action.

## Limits

- The profile does not appear in the publisher's artifact table. Declare it as a global profile
  (`global:` in `sushi-config.yaml`, parameter `globals-in-artifacts: true`) to have it listed on the artifacts page,
  and use the data file to link it to its page
- The fragments contain inline scripts (tree filter). On the HL7 ci-build these are reported as warnings; with your
  own hosting they are harmless
- Links to resources of other packages use `simplifier.net/resolve` when the package does not state a web URL
- Every run builds the helper IG from scratch: about one to three minutes depending on the dependencies
